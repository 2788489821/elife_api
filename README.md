# elife_api — 接口自动化测试框架

基于 **Python + requests + pytest** 的接口自动化测试项目，采用 **AOM（API Object Model）** 分层设计，覆盖电商后台管理系统（SMP）的登录、设备类型、业务规则三个模块的接口，共 **21 条用例**（17 通过 + 4 xfail），并集成 **Allure** 生成测试报告。

## 技术栈

| 类别 | 技术 |
|------|------|
| 语言 | Python 3.14 |
| 接口请求 | requests 2.34 |
| 测试框架 | pytest 9.2 |
| 测试报告 | allure-pytest 2.16（Allure CLI 2.46） |
| 设计模式 | AOM（BaseAPI + 各模块 API 封装类） |

## 目录结构

```
elife_api/
├── cfg.py                      # 环境配置（被测系统地址、各接口 URL）
├── conftest.py                 # fixture：token 获取、临时数据创建与自动清理
├── lib/
│   ├── base_api.py             # BaseAPI 基类：封装通用请求方法
│   ├── login_api.py            # 登录模块接口封装
│   ├── device_model_api.py     # 设备类型模块接口封装
│   └── service_rule_api.py     # 业务规则模块接口封装（含计费规则构造）
└── cases/                      # 测试用例层（只写业务断言，不碰请求细节）
    ├── test_login.py           # 登录接口
    ├── test_device_model.py    # 设备类型接口
    └── test_service_rule.py    # 业务规则接口
```

## 被测系统

本地部署的电商后台管理系统（练习环境，来自白月黑羽软件测试教程）的 REST 接口，地址配置在 `cfg.py`。接口文档通过浏览器 F12 抓包分析整理，再据此设计探测脚本与用例。

## 快速开始

```bash
# 1. 安装依赖
pip install requests pytest allure-pytest

# 2. 启动被测系统（默认 127.0.0.1:8234）

# 3. 运行全部用例并生成 allure 结果
pytest --alluredir=tmp_allure

# 4. 查看 allure 报告
allure serve tmp_allure
```

## 测试范围

| 模块 | 用例数 | 覆盖点 |
|------|--------|--------|
| 登录 | 7 | 正常登录；空用户名、空密码、错误密码、不存在用户等异常入参，校验返回码与提示文案 |
| 设备类型 | 6 | 列表查询、新增、删除，含非法参数校验 |
| 业务规则 | 8 | 新增（多计费规则参数化）、关键字筛选、删除 |
| **合计** | **21** | 17 通过 + 4 xfail（对应 4 个后端缺陷，见下） |

## 发现的真实后端缺陷（4 个）

对被测系统做接口测试时，通过 F12 抓包分析接口文档并设计边界用例，发现以下后端缺陷，均以 `xfail` 标记管理并跟进：

| # | 缺陷 | 位置 | 说明 |
|---|------|------|------|
| 1 | 新增数据时不校验 typeid 是否存在 | 设备类型接口 | 传入不存在的 typeid，错误数据仍可正常入库 |
| 2 | 新增数据时不校验 type_id 是否存在 | 业务规则接口 | 同上 |
| 3 | 删除数据时不校验 id 是否存在 | 设备类型接口 | 删除不存在的 id，接口仍返回成功 |
| 4 | 删除数据时不校验 id 是否存在 | 业务规则接口 | 同上 |

另有 2 个疑似问题：登录接口空入参时返回的提示文案语义不准确（空用户名应提示"用户名不能为空"，实际返回"用户名不存在"），已在用例中标注。

## 框架设计要点

- **AOM 分层**：每个模块的接口请求封装在 `lib/` 对应类中，用例层只调用方法做断言，接口地址/参数变更只改一处。
- **token 统一管理**：`token` fixture（module 级）自动登录获取，全部用例共享。
- **测试数据自动清理**：新增数据的用例通过 fixture 自动创建临时数据并在用例结束后删除（删除失败重试一次），保证接口数据环境可重复执行，不留脏数据。
- **参数化驱动**：登录异常入参、业务规则计费类型均用 `@pytest.mark.parametrize` 数据驱动，加用例只需加一行数据。
- **缺陷管理**：已确认的后端缺陷用 `@pytest.mark.xfail(reason=...)` 标记，报告中原样可见，开发修复后去掉标记即可转正。
- **Allure 报告**：用例标注 feature/story/severity，核心流程拆分 step，报告可直接给开发/产品看。
